# Cutover checklist

**Your instance's live punch list.** Everything the scaffold defers because it needs real credentials,
accounts, or money. The scaffold boots and is fully testable without any of it — nothing here is a blocker,
each is a row.

The rows below are the ones essentially every instance needs, pre-filled with the _deferred verification_
each one owes. Fill in `What unlocks it` with your own owner, work them in roughly the order given, and add
rows as your product acquires dependencies.

## The pattern

> **Row** = item name · what it is · what unlocks it · **the exact verification that was deferred**

The last column is the load-bearing one, and the discipline worth copying: **name the proof, not just the
task.** "Set up the mail provider" is a task; "a real send through the email port, with DKIM/SPF verified
on the domain" is a proof. Until a row's proof is met, the related real adapter is **authored but
unverified** — treat it accordingly. Real adapters carry an `AUTHORED — CUTOVER` header comment until
their row closes.

Item names stay vendor-neutral (`email-outbound`, not the vendor you picked) so a row survives changing
vendors; the vendor-specific detail belongs in the proof column, where it is doing work.

A row is worked, not just ticked. This is the level of detail one deserves once you fill it in — note the
owner, the date and the evidence in `What unlocks it`, and a proof column that has been thought through
rather than restated:

| ⬜     | `db-role-not-superuser`         | The role in `DATABASE_URL` holds neither `SUPERUSER` nor `BYPASSRLS`                    |                 | `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user` returns `f, f` against the deployed database. Either attribute bypasses row-level security outright — including `FORCE` — so tenant isolation would be off in production while every local gate stays green, because neither pglite nor the contract suite can see the deployed role. `infra/stack.ts` wires `DATABASE_URL` to the cluster's MASTER credentials, so the app connects as the table owner by default and `FORCE` is the only thing between that connection and every tenant's rows: create a dedicated non-superuser role for the application and migrate with a separate one. That role must be able to switch to `app_user`, which every `withTenant` does, and it cannot grant itself that because it did not create `app_user`. The grant must be made by the role that CREATED `app_user` (the migrating owner, whose migration 0001 created it; on Postgres 16+ its creator holds ADMIN on it), or by any role holding ADMIN on `app_user`: `GRANT app_user TO <app role> WITH SET TRUE, INHERIT TRUE;`. INHERIT TRUE because the app reads `tenants`, `organizations` and `service_keys` before any tenant is set, through `app_user`'s grants. The app role must own nothing. The migrator itself is granted the switch by migration 0015 (ADR-0004, 2026-11-16 addendum). Check: as the app role, `BEGIN; SET LOCAL ROLE app_user; ROLLBACK;` succeeds. Two databases on ONE cluster (staging and production on one Aurora cluster) migrated by different owners: `app_user` is cluster-wide, so only the owner that migrated first created it and holds ADMIN. The second owner's migration stops at 0015, rolls back whole, and prints the statement to run. As the first owner, or any role with ADMIN on `app_user`, run that statement (`GRANT app_user TO <second owner> WITH SET TRUE, INHERIT FALSE;`), then re-run the second owner's migrations. A logical dump (`pg_dump`) restored into another cluster carries the migration ledger but no roles: `pg_dump` dumps one database, and roles and their memberships are cluster-wide. So the ledger says 0001 and 0015 ran, neither runs again, and neither `app_user` nor anyone's switch to it came along. As the migrator, create `app_user` before restoring (`CREATE ROLE app_user NOLOGIN;`), so the dump's grants to it apply. After restoring, still as the migrator, run `GRANT app_user TO CURRENT_USER WITH SET TRUE, INHERIT FALSE;` (what 0015 does), then the app role's GRANT above. After ANY restore, run the check as the app role and as the migrator. |
