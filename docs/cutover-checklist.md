# Cutover checklist

**Your instance's live punch list.** Everything the scaffold defers because it needs real credentials,
accounts, or money. The scaffold boots and is fully testable without any of it — nothing here is a blocker,
each is a row.

The rows below are the ones essentially every instance needs, pre-filled with the _deferred verification_
each one owes. Fill in `What unlocks it` with your own owner, work them in roughly the order given, and add
rows as your product acquires dependencies.

## The pattern

> **Row** = item name · what it is · what unlocks it · **the exact verification that was deferred**

The last column is the load-bearing one, and the discipline worth copying: **name the proof, not just the
task.** "Set up the mail provider" is a task; "a real send through the email port, with DKIM/SPF verified
on the domain" is a proof. Until a row's proof is met, the related real adapter is **authored but
unverified** — treat it accordingly. Real adapters carry an `AUTHORED — CUTOVER` header comment until
their row closes.

Item names stay vendor-neutral (`email-outbound`, not the vendor you picked) so a row survives changing
vendors; the vendor-specific detail belongs in the proof column, where it is doing work.

A row is worked, not just ticked. This is the level of detail one deserves once you fill it in — note the
owner, the date and the evidence in `What unlocks it`, and a proof column that has been thought through
rather than restated:

| Status | Item             | What it is                                                        | What unlocks it                                                            | Deferred verification                                                                                                                                                                                                                                                                                          |
| ------ | ---------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅     | `email-outbound` | Sending domain + API key (names in `apps/<app>/config/params.ts`) | DONE 2026-08-01, platform owner: domain delegated, key in the secret store | A real send through the `email` port landed in an external inbox with DKIM and SPF passing on the domain; the rendered react-email template read correctly in a real client, not only in the preview server; a bounce to an invalid address was observed, so the failure path is known before a user finds it. |
